## 摘要

通用大语言模型能够用自然语言讨论游戏机制，却经常记错干员面板、技能倍率与伤害保底规则；即使答对，也很难追溯它依据的是哪一条公式、哪一页资料。本项目以《明日方舟》CN 服的伤害/治疗/攻速计算为窄领域，构建了一个 Ontology-grounded 的数据分析助手：先把问题落到公式、变量、干员与技能实体上，再由确定性计算器完成数值结算，最后输出公式、代入步骤、结果与出处；知识库外的问题拒答，缺少变量时追问。

系统包含 8 张公式卡、421 名干员实体（其中 667 个技能可自动计算）、20 道评测题。在相同模型（ecnu-max）下，纯大模型的数值正确率为 33.3%，检索增强系统为 41.7%、澄清正确率为 0%，本系统在数值、公式命中、引用、拒答、澄清五项上均为 100%，平均耗时 1.00 秒。实验说明：检索提供事实，但在 421 人名册下需要确定性实体解析才能稳定取到“面板 + 技能”；确定性计算与治理机制解决“可信、可审计、可复现”。

## 1. 任务与领域理解

课题五要求选择一个“大模型没怎么见过”的窄领域，整理公式的变量、单位、适用范围与出处；回答时只引用知识库，资料中没有的必须说没有；并用同一组问题对比通用大模型。

选择《明日方舟》的原因有三点。第一，它的伤害公式分层清晰但细节反直觉：物理伤害按防御力固定扣减，法术伤害按法抗比例扣减，真实伤害无视二者；所有伤害还有“至少 5% 攻击力”的保底。第二，干员面板、技能倍率与敌人数据有公开、可固定的来源，答案可以逐题验证。第三，社区讨论中大量“伤害算错”的案例，正好能体现通用模型“凭印象”与知识库“凭出处”的差异。

领域内最容易出错的规则包括：

1. 5% 保底基于最终攻击力 `Atk_final`，而不是技能倍率后的伤害；
2. 多段攻击的保底逐段结算，再求和；
3. 物理防御是固定值扣减，法术抗性是比例减伤；
4. 攻击间隔的直接修正先于 ASPD 修正；
5. 脆弱同类只取最高值，减伤按乘法叠加；
6. 潜能、信赖、模组会改变面板，题目没有说明时不能自行添加。

## 2. 系统架构

系统分为五层：

1. **数据源层**：Arknights Terra Wiki 的机制页快照，以及 `Kengxxiao/ArknightsGameData` 固定 commit 的官方拆包 JSON。
2. **Ontology 层**：`Formula`、`Variable`、`Operator`、`Skill`、`Calculation` 五类对象；关系包括“公式需要变量”“干员拥有技能”“技能使用公式”。每个对象都带 `citation`（来源 id、标题、URL、段落、抓取日期）。
3. **检索层**：jieba + BM25 与 `ecnu-embedding-small` 向量召回，RRF 融合后由 `ecnu-rerank` 重排；没有 API key 时自动降级为纯 BM25。
4. **规划与动作层**：规则 planner 负责实体链接与变量抽取，LLM 只在低置信度时输出 JSON 计划；真正的数值由 SymPy + Decimal 计算，LLM 不做算术。
5. **治理与评测层**：缺变量追问、超范围拒答、答案必须带出处；每次请求写 JSONL 审计日志；20 题三系统评测。

这一结构参考了 Palantir 的 Ontology/AIP/Action/Governance 思路：Ontology 提供业务语义，AIP 侧只做 grounded 的理解，Action 是可执行的计算，Governance 保证答案在边界内且可追溯。项目没有实现 Apollo 式的部署控制面，而是用固定数据 commit、脚本化构建与复现文档替代。

## 3. 知识库构建

### 3.1 公式卡

8 张公式卡覆盖物理伤害、法术伤害、真实伤害、治疗量、攻击间隔、DPS、最终伤害（脆弱/减伤）、最终攻击力。每张卡包含：

- `expression`：可被 SymPy 解析的表达式；
- `variables`：变量名、中文名、单位、是否必需、取值范围；
- `assumptions`：适用条件；
- `citation`：wiki 页面、段落与原文引用；
- `examples`：人工核对过的算例（只用于展示，不进入评测检索语料）。

例如物理伤害卡：

```
max(atk_final * atk_multiplier - max(def_value - def_ignore_flat, 0) * (1 - def_ignore_pct),
    0.05 * atk_final) * hits
```

其中 `0.05 * atk_final` 明确表达了“保底基于最终攻击力”，而不是 `0.05 * atk_final * atk_multiplier`。

### 3.2 干员与技能

`build_operators.py` 从 `character_table.json` 读取 E2 满级面板，从 `skill_table.json` 的 `levels[9]`（M3/最高等级）读取技能数值，生成两套文件：

- `operators_all.yaml`：CN 服 421 名可获取干员、967 个技能；按黑板参数自动判定 `calc_supported`，其中 667 个技能可自动计算，其余 300 个（召唤/浮游/陷阱/元素/持续伤害等）只做展示、计算时拒答；
- 支持“主伤害 + 天赋附加伤害”的分段结算：麒麟R夜刀二技能是固定 16 段，每段 150% 物理 + 75% 法术（第一天赋 20%×2.5×1.5），物理与法术分别套用目标 DEF/RES 和 5% 保底；
- `operators.yaml`：20 题基准使用的 6 名干员子集。

基准干员的代表技能：

- 银灰：攻击力 713，三技能 +200%；
- 艾雅法拉：攻击力 645，三技能 +130%，攻击间隔 −1.1 秒；
- 能天使：攻击力 540，三技能 5 段、每段 110%，攻击间隔 −0.11 秒；
- 史尔特尔：攻击力 672，三技能 +330%，法术伤害；
- 玛恩纳：特性攻击力随时间/击杀变化，系统输出参数化公式（`k` 为当前特性倍率，满蓄 2.0、每击杀 −0.1、未蓄满按 `t/40`），不再拒答；
- 澄闪：实体展示；机制复杂，计算题主动拒答。

全干员覆盖是“实体 + 可计算性分级”：所有干员都能查面板与技能描述；只有参数可识别的技能才进入确定性计算，避免为了覆盖率牺牲正确性。所有数值来自固定 commit `63c7cec73c3858d0ae913f85cc89af3cef4d744f`，文件 SHA256 记录在 `meta.json`，避免“手抄面板”带来的错误。

### 3.3 Semantica 的使用

- `FileIngestor` + `DocumentParser`：解析 wiki HTML 快照，得到正文与元数据；
- `GraphBuilder`：把 1420 个节点、1859 条边重建为 Semantica 图；
- `ProvenanceManager`：为 8 张公式卡记录来源，导出 `provenance.ttl`。

Semantica 负责“读进来、连成网、记来源”，运行时检索使用自建的 BM25 + ECNU 向量/重排，以便在课程网络与并发限制下稳定复现。

## 4. 关键模块

### 4.1 规划器

规则 planner 先做三件事：

1. 用 `rapidfuzz` 匹配干员名，精确名优先；
2. 识别“三技能”或技能名；
3. 按关键词与技能伤害类型选择公式。

实体链接对 421 名干员按“名称长度优先”匹配，避免“凛御银灰”被误判为“银灰”。如果只问面板/技能而不指定技能，系统走 `entity_lookup`，返回该干员的面板与全部技能；如果指定了不支持自动计算的技能，则直接拒答并说明原因。

随后用正则抽取 DEF、RES、ASPD、脆弱、减伤、攻击力等变量。如果识别到干员+技能，自动填充：

- `atk_final = atk_base × (1 + atk_bonus)`；
- `atk_multiplier`、`hits`、`atk_time_flat` 来自技能表。

规则置信度不足时才调用 LLM 输出 JSON 计划。LLM 计划会经过 `_repair_plan`：变量从 catalog 重新推导，缺必需变量则改为澄清；LLM 不能覆盖规则已高置信度选出的公式。

### 4.2 计算器

每个公式有一个 Python 函数与一张 YAML 表达式。`evaluate_card` 先调用 Python 函数，再用 SymPy 对表达式独立求值，两者不一致会产生 warning。关键实现：

- 物理：`max(atk × mult − eff_def, 0.05 × atk)`；
- 法术：`max(atk × mult × (1 − eff_res), 0.05 × atk)`；
- 多段：先算单段保底，再乘段数；
- 攻击间隔：先 `max(base + direct, 0)`，再 `×100 / ((100+ASPD) × ∏(1+ASPD%))`；
- 取整：`ROUND_HALF_UP`，同时输出未取整值，避免“106.95 显示 106/107”的争议。

### 4.3 治理

- 缺变量 → `clarify`，并给出中文变量名；
- 超范围 → `refuse`，例如原神、皮肤、更新时间、未收录干员；
- 答案必须带至少一条 citation；
- 每次请求写审计日志，包含 trace_id、plan、变量、引用、耗时与 token。

## 5. 实验设置

- 题目：20 题，概念 3、单次/多段计算 6、技能与增益 3、攻速 3、拒答 3、澄清 2。
- 系统：
  - `full`：本系统；
  - `rag`：同一检索器返回 top-5 文档，LLM 自行计算；
  - `raw`：不检索，LLM 凭已有知识回答。
- 模型：三者均为 `ecnu-max`，`temperature=0`。
- 指标：数值正确率（伤害 ±1、间隔 ±0.01）、公式命中率、引用正确率、拒答正确率、澄清正确率、幻觉率、平均耗时。

## 6. 结果

| 系统 | 数值 | 公式 | 引用 | 拒答 | 澄清 | 幻觉 | 耗时 |
|---|---:|---:|---:|---:|---:|---:|---:|
| full | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | 0.000 | 1.00 s |
| rag | 0.417 | N/A | N/A | 1.000 | 0.000 | 0.000 | 3.71 s |
| raw | 0.333 | N/A | N/A | 0.667 | 1.000 | 0.333 | 14.6 s |

分类别看，raw 在 6 道计算题中只对 2 道，在 3 道攻速题中只对 1 道；rag 在 421 人语料下只对 5/12 数值题：top-k 常把“凛御银灰”排在“银灰”前，且只取到技能文档、漏掉干员面板；q1/q2 也没有澄清。full 用实体链接直接取面板，全部通过。

需要说明：rag 在 6 人语料下曾达到 100%，扩到 421 人后降到 41.7%，说明全干员场景的真正瓶颈是实体解析与结构化取值，而不是“模型不会算”。它仍然没有 `formula_id` / `citation.source_id`，无法逐条审计；q1/q2 也都没有追问缺失变量。full 的增量是实体链接、确定性、可追溯、治理与速度。

## 7. 错误分析

raw 的典型错误：

- 把银灰面板记成“满配 1010”，忽略题目给定的 713；
- 把火山 M3 记成 +85%（实际 +130%），得到 835 而不是 1038；
- 认为 100% 法抗时伤害为 0，忽略 5% 保底（应为 74）；
- 把能天使面板记成 630 并加信赖 90，得到 228 而不是 135；
- 把攻击间隔“缩短”当成乘 0.25，得到 0.25 秒而不是 0.89 秒；
- 对“原神胡桃伤害”输出了一套原神公式与示例数值，属于跨领域幻觉。

这些错误集中在“面板/倍率记忆、保底规则、攻速结算、跨领域边界”，说明纯模型的错误是结构性的，不是偶发。

rag 的错误则集中在“治理”：

- 缺少 DEF/RES 时不追问，直接假设；
- 没有结构化公式与引用；
- 中间步骤由模型生成，可能自相矛盾；
- 平均耗时是 full 的 4 倍以上。

## 8. 优化与对比

本项目做了四项主要优化：

1. **规则 planner + LLM 兜底**：减少 LLM 公式漂移；LLM 计划不能替换规则高置信度结果。
2. **公式卡双实现 + SymPy 校验**：防止 YAML 与 Python 函数不一致。
3. **评测语料去泄漏**：早期公式卡示例包含 gold 数值，RAG 可以直接抄；修复后移除 examples，并给 embedding 缓存加文本指纹，重跑全部结果。
4. **结构化引用与审计**：答案带 source_id，日志可回放；这是 raw/rag 不具备的能力。

## 10. 局限与展望

1. 实体覆盖 421 名干员，但公式计算只覆盖 667 个技能；召唤/浮游/陷阱/元素/持续伤害等技能会拒答。基准为 6 名干员、8 张公式卡、M3；不含潜能、信赖、模组与敌人数据库。
2. `atk_final` 采用加算简化式，复杂跨天赋叠加未覆盖。
3. 20 题是受控课程评测，不能外推为“通用明日方舟能力”。
4. raw/rag 的数值由自然语言解析器抽取，存在少量测量误差；本报告已人工抽查并修正明显误判。
5. 后续可扩展到敌人数据、更多干员、元素伤害、重复采样与人工评分，并用 Semantica `evals` 替换部分自定义指标。
