# 评测协议与结果

## 1. 协议

- **题目**：`eval/questions.jsonl`，20 题，6 类：概念 3、单次/多段计算 6、技能与增益 3、攻速 3、拒答 3、澄清 2。
- **模型**：三种系统均使用 `ecnu-max`，`temperature=0`。
- **系统**：
  - `full`：本系统（检索 + 规则/LLM 规划 + 确定性计算 + 引用/审计）；
  - `rag`：同一检索器返回 top-5 文档，LLM 自行计算并回答；
  - `raw`：不检索，LLM 凭已有知识回答。
- **评分**：
  - 数值正确：与 gold 的绝对误差 ≤ tolerance（伤害 1 点，间隔 0.01 秒）；
  - 公式命中：`plan.formula_id ∈ question.formula_ids`（仅 full 有结构化 plan）；
  - 引用正确：答案 citation 的 `source_id ∈ question.citation_ids`（仅 full 测量）；
  - 拒答正确：应拒答题是否拒答；
  - 澄清正确：应追问题是否追问（full 看 intent=clarify；基线用文本启发式）；
  - 幻觉：应拒答题却给出了答案；
  - 耗时：单题端到端墙钟时间。

## 4. 如何解读

### 4.1 检索是必要条件

`raw` 只有 33.3% 数值正确率，典型错误包括：

- 把银灰面板攻击力记成“满配 1010”，导致 DEF=2100 时算出 930（正确应为 107）；
- 把艾雅法拉火山 M3 记成 +85%（正确 +130%），算出 835（正确 1038）；
- 认为 100% 法抗时伤害为 0，忽略 5% 保底（正确 74）；
- 能天使三技能攻击力/倍率记错，五连射总伤算成 228（正确 135）；
- 攻击间隔把“缩短”当成乘 0.25 或 0.85，得到 0.25/0.85 秒（正确 0.89 秒）；
- 对“原神胡桃伤害”给出了一套原神公式与示例数值（跨领域幻觉）。

这些错误与社区讨论中常见的“LLM 记错干员数值/技能倍率/保底规则”一致，说明**只靠模型记忆不可靠**。

### 4.2 强检索 + 强模型可以算对，但不等于可交付

`rag` 在 6 人语料下曾达到 100%；扩到 421 人/1396 篇文档后降到 **41.7%**。原因不是模型变弱，而是 top-k 检索在大量同名/alter 干员中发生歧义（例如“凛御银灰”排在“银灰”前），并且只取到技能文档、漏掉干员面板。这个结果说明全干员场景下“检索”本身不够，需要实体解析与结构化取值。

但 `rag` 仍有明显缺口：

- **澄清 0/2**：q1 直接假设 DEF=0 给出 2139，q2 直接假设防御并算出 3373.4，而不是追问缺少的 `damage_per_hit`/DEF。
- **没有结构化公式命中与引用**：答案可能提到来源，但没有可校验的 `formula_id` 与 `citation.source_id`，无法做逐条审计。
- **不可复核的算术**：中间步骤由模型生成，换一次采样可能得到不同结论；本实验中 n3 就出现过开头写 1043.61、结尾改成 1038.45 的自相矛盾。
- **更慢**：3.71 s vs 1.00 s，因为每题都要把 8 篇检索文档交给模型重写推理。

`full` 的增量价值因此不在“数值更高”，而在：

1. **确定性**：同一输入得到同一结果，计算由 SymPy/Decimal 执行；
2. **可审计**：每题有 formula_id、变量绑定、逐步 trace、source_id；
3. **治理**：缺变量必须追问，超范围必须拒答，答案必须带出处；
4. **速度**：模板化输出，无需让模型重写算术。

### 4.3 full 的 100% 不等于“通用能力 100%”

20 题围绕 6 名基准干员设计，属于受控课程评测；实体库虽覆盖 421 名干员，但复杂技能会拒答计算。RAG 的下降主要来自实体歧义与上下文稀释，不应外推为“RAG 一定差”。报告应同时说明这一点。

## 5. 效度威胁

| 威胁 | 说明 | 缓解 |
|---|---|---|
| 小样本 | 20 题，无法支撑显著性检验 | 报告描述性统计；不宣称统计显著 |
| 题目与知识库同源 | 题目围绕已整理公式设计 | 明确范围；增加拒答/澄清题检验边界 |
| 数据泄漏 | 公式卡示例曾包含 gold 数值，进入 RAG 上下文 | 已从 corpus 移除 examples，增加 embedding 文本指纹并重跑 |
| 基线不公平 | raw 无检索、rag 有检索；模型相同但信息量不同 | 明确三种系统的信息条件；raw 只用于说明“无检索”下限 |
| 解析启发式 | raw/rag 的数值从自然语言中抽取，可能误判 | 人工抽查失败样本；保留原始 prediction 供复核 |
| 单次运行 | LLM 有随机性（即使 temperature=0） | 报告单次结果；后续可重复 3 次取均值 |
| 版本漂移 | 游戏更新会改变数值 | 固定 commit 与抓取日期 |

## 6. 复现

```bash
python scripts/run_eval.py --system full
python scripts/run_eval.py --system rag
python scripts/run_eval.py --system raw
python scripts/make_report_assets.py
```

每次运行生成 `results/eval_<system>_<timestamp>.json`；`make_report_assets.py` 取每个系统最新一份，生成 CSV 与 Markdown 表格。若要复现本文数字，请使用文中列出的文件名。
